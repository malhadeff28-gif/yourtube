# How live curation works

`server.js` watches locally stored Codex Desktop user-message events while live mode is enabled. A 12-second debounce coalesces nearby events; the system does not run on a schedule. It processes at most one update at a time, keeps a small in-memory queue, and uses up to three recent user messages from the same chat to interpret follow-ups. Pausing clears the in-memory queue and recent messages; delayed discovery or file rewrites can still cause older or paused text to be read later. The service attempts to save the Live setting across restarts, but a settings write can fail.

To determine whether an event is relevant, the service sends short, best-effort-redacted user-text excerpts and existing feed context IDs, names and tasks to an ephemeral read-only Codex invocation. The existing context fields are not redacted. Connected apps, plugins and shell tools are disabled. The classifier treats the message as untrusted data and proposes a general public search phrase. A separate Codex invocation receives only that phrase and uses web search to find real video IDs; the service checks IDs using YouTube oEmbed before updating `dist/feed.json`. Search may take a minute or more. The separate Codex invocation may send the phrase or derived queries to search providers without a user review step; redaction/generalization are imperfect, and the README explains the privacy boundary.

`dist/feed.json` stores inferred context and verified video metadata. Edits and saved videos remain in browser-local storage. The service atomically writes validated feed updates and sends a local server event, so an open page updates without reloading. Existing project IDs stay stable when the classifier matches them. If access, inference, search, verification or validation fails, the service reports a status and keeps the prior feed. The app does not read screenshots or browser pages. Chat format, search availability and YouTube availability can change.

The event watcher covers local Codex Desktop session files, not ChatGPT web/mobile chats or remote-only conversations. It normally starts at the end of files found on startup, but delayed discovery or an in-place rewrite can cause older or paused text to be read later. The optional user-level launch service can run after login. The `Live` control pauses processing and attempts to save that setting across restarts. `scripts/service.py remove` leaves an existing service and its file untouched; see the README for manual inspection and removal. A fresh public checkout starts paused.
