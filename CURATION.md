# How live curation works

`server.js` watches locally stored Codex Desktop user-message events while live mode is enabled. A 12-second debounce coalesces nearby events; the system does not run on a schedule. It processes at most one update at a time, keeps a small in-memory queue, and uses up to three recent user messages from the same chat to interpret follow-ups. Messages that arrive while paused are normally discarded, but an in-place file rewrite can cause older or paused text to be read later. Live starts paused on each service launch.

To determine whether an event is relevant, the service sends a short, best-effort-redacted user-text excerpt and the local feed's stored project IDs, names, and tasks to an ephemeral read-only Codex invocation. Project names and tasks receive best-effort redaction; IDs are sent unchanged. Redaction can miss sensitive information. Connected apps, plugins and shell tools are disabled. The classifier treats the message as untrusted data and proposes a general public search phrase. After explicit Live consent, the normal UI selects automatic mode: a separate search-enabled Codex invocation receives the automatically proposed general search phrase without per-search approval. When verified videos are found, automatic mode adds them to the selected stored project without changing that project’s existing name, task or note, or creates a new project if needed. An existing project that changes during processing is not overwritten. For a new Live project the service allocates a full UUID and checks it against the latest server feed before writing. Browser-only IDs are not visible to that check, and uncoordinated external feed writers remain outside its protection. That invocation may send the phrase or queries derived from it to search providers. The legacy review-mode API can still request approval; its pending review expires after ten minutes and is canceled by pausing. The service checks video IDs using YouTube oEmbed before updating `dist/feed.json`. Redaction/generalization are imperfect and there is no per-search review in automatic mode.

A separate user-initiated manual search is available while Live is paused. It does not read chats or project details: after the user enters a general public phrase and selects Search, that phrase is sent to the search-enabled Codex invocation and may be sent to web search providers. Candidate IDs are verified using YouTube metadata. Results remain in service memory for up to ten minutes, without changing the server feed; the user can open a candidate in a new YouTube tab, which connects to YouTube, or select individual videos to save to a project in browser storage. Manual searches do not run concurrently with Live work. Local dismissal does not cancel an in-flight search.

`dist/feed.json` stores inferred context and verified video metadata. Edits and saved videos remain in browser-local storage unless the user explicitly copies a saved project name and task to an existing matching project in the local Live feed; browser-only projects cannot yet be copied, and notes are not copied. Copying does not start Live and refuses to overwrite a changed project or interrupt active curation. The service atomically writes validated feed updates and sends a local server event, so an open page updates without reloading. Existing project IDs stay stable when the classifier matches them. If access, inference, search, verification or validation fails, the service reports a status and keeps the prior feed. The app does not read screenshots or browser pages. Chat format, search availability and YouTube availability can change.

The event watcher covers local Codex Desktop session files, not ChatGPT web/mobile chats or remote-only conversations. It normally starts from the end of existing files, but an in-place rewrite can cause earlier text to be read later. The optional user-level launch service can run after login. The `Live` control pauses processing for the current run. The service helper refuses to stop or remove an existing LaunchAgent automatically because its file alone cannot prove which job is loaded; inspect the loaded job and agent file before removing either manually. Every service launch starts paused.
